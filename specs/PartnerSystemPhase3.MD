# Partner System Phase 3 Specification

## Purpose

Phase 3 turns the partner relationship from a passive read-only connection into an active accountability loop.

By the end of Phase 2:

- the invite lifecycle exists
- an accepted invite creates a live `goal_partnerships` record
- the partner can read a safe snapshot of the goal
- both users can pause, unpause, unlink, and control `notify_on_alerts`

Phase 3 adds:

- hybrid server-side alert evaluation
- in-app partner notifications
- one-tap encouragements
- alert observability and suppression controls

This phase must preserve the existing v1 rules:

- one partner per goal
- signals-only visibility
- in-app only after the invite email
- no free-text partner messaging
- silent unlink/removal
- no client-only alert generation

## Phase 3 In Plain Terms

Phase 3 answers one question:

"Once a partnership exists, how does the system decide when the partner should be nudged to check in?"

The answer is:

1. The backend evaluates the goal against server-known activity signals.
2. If an accountability condition is true, it decides whether an alert should be created.
3. If the alert is not suppressed by grace rules, rate limits, or preferences, the partner receives an in-app notification.
4. The partner can open the linked partnership snapshot and optionally send a preset encouragement.

Phase 3 is not about showing more private data.
It is about using the already-approved safe snapshot signals to decide when the partner should be prompted.

## Goals

- Detect meaningful accountability risk using server-trusted data only.
- Notify the partner in-app with neutral, non-shaming language.
- Respect `status`, `notify_on_alerts`, and unlink state immediately.
- Prevent spam using grace windows, dedupe rules, and per-goal cooldowns.
- Allow one-tap encouragements without introducing free-text messaging.
- Record enough evaluator state to debug false positives and silent suppressions.
- Stay compatible with the app's offline-first direction by avoiding unnecessary backend-triggered evaluations on routine read endpoints.

## Non-Goals

- No push notifications in v1.
- No email notifications after the original invite email.
- No free-text partner-to-user messaging.
- No new partner visibility beyond the existing snapshot contract.
- No partner edits to goals, events, or logs.
- No client-side alert generation that can diverge from backend state.

Push delivery should remain a future-compatible extension point, but it is not part of this phase.

## Architectural Rule: One Schedule Truth

Phase 3 must not introduce a third independent recurrence implementation.

The alert evaluator needs the same concept of:

- what dates were scheduled
- which scheduled dates count as missed
- when a streak ends
- how points expected by today are derived

The backend already has this logic inside `GoalPartnerSnapshotService`.
Before or during Phase 3, the recurrence and occurrence-generation logic should be extracted into a shared backend service or helper so both:

- snapshot generation
- alert evaluation

consume the same date-generation path.

This is mandatory to avoid drift between:

- the partnership detail screen
- the alert engine
- future analytics/debugging tools

## Product Principles

Phase 3 alerts must follow these principles:

- Supportive, not punitive.
- Actionable, not vague.
- Private by default.
- Sparse rather than spammy.
- Based on actual received logs, never local or assumed client state.

The alert should answer:

- "Should the partner probably check in?"

It should not answer:

- "What did the user write?"
- "How did they describe how they feel?"
- "What exactly happened in their private logs?"

## Alert Types

Phase 3 supports these alert types:

1. `streak_broken`
2. `consecutive_misses`
3. `behind_pace`
4. `inactivity`

### `streak_broken`

Meaning:

- the user had a real scheduled streak in progress
- a scheduled occurrence that can now be judged has no matching log
- that miss ends the current streak

Why it exists:

- streak loss is emotionally meaningful and a strong accountability signal

Default threshold:

- eligible as soon as the first missed scheduled occurrence becomes evaluatable after the grace window

### `consecutive_misses`

Meaning:

- multiple scheduled occurrences in a row have gone unlogged

Why it exists:

- a single miss may be noise
- repeated misses are a clearer sign of disengagement

Default threshold:

- `2` consecutive missed scheduled occurrences

This is the primary miss-based partner alert because it captures both:

- whether the streak was broken at all
- how deep the current miss pattern has become

### `behind_pace`

Meaning:

- the user is logging enough below expected progress that it is no longer just normal variance

Why it exists:

- some goals degrade gradually without obvious streak loss

Default threshold:

- `pace_status === 'behind'`
- `pace_delta <= -2.0`
- `points_expected_by_today >= 4.0`

The minimum expected points guard exists so very new or very small goals do not alert too early.

### `inactivity`

Meaning:

- the user has not submitted any log for several days

Why it exists:

- some goals do not produce a clean missed-occurrence pattern
- inactivity is one of the simplest and most intuitive accountability signals

Default threshold:

- `inactivity_days >= 3`

If the user has never logged, inactivity should be derived from goal start or the first active scheduled period, not from partnership creation time.

## Shared Definitions

### Scheduled occurrence

A scheduled occurrence is a concrete date generated from:

- `event.scheduled_for`
- `event.repeat.frequency`
- `event.repeat.times_per_week`
- `event.repeat.duration_in_weeks`

This is the same model used by the Phase 2 snapshot.

### Logged occurrence

A scheduled occurrence is considered logged if a matching owner feedback row exists for:

- the same `event_id`
- the same scheduled date

### Successful occurrence

For pace and points calculations, success keeps the existing Phase 2 meaning:

- `completed`
- `partial`
- `struggled`
- `nailed_it`

### Missed occurrence

A scheduled occurrence is considered missed only when:

- the occurrence date has fully passed
- the grace window has fully passed
- there is still no matching log

An occurrence due today must not count as missed yet.

This matches the current streak rule that "today without a log yet" does not immediately break the streak.

## Grace Window And Time Semantics

Because the current scheduling model is date-based, not time-of-day based, the evaluator should use a simple post-date grace rule in a single canonical backend time basis for v1.

Default v1 rule:

- a due occurrence is not eligible for miss-based alerts on the same calendar day
- once the date rolls over, apply an additional `6` hour grace before treating it as missed

Recommended config key:

- `PARTNER_ALERT_GRACE_HOURS=6`

Canonical-time rule for v1:

- store and evaluate alert timing in a single backend timezone, preferably UTC
- frontend may convert timestamps for display only
- user timezone moves and historical timezone correction are out of scope for v1

The system should still prefer a false negative over a false positive when a boundary is ambiguous.

## Evaluation Sources

Phase 3 uses a hybrid evaluation model with two v1 sources:

1. `log_submit`
2. `scheduled_scan`

### `log_submit`

Triggered after a successful `EventController::storeEventFeedback`.

Why:

- the most accurate point to evaluate fresh state
- catches pace recovery and avoids stale alerts

### `scheduled_scan`

Triggered by a scheduled backend job scanning candidate partnerships.

Why:

- prevents users from dodging accountability simply by avoiding the app

Explicit app-open pings can be introduced later if needed, but v1 should not bind evaluator work to high-churn read endpoints like `getGoals`.

## Evaluation Eligibility

A partnership is only eligible for alert creation when all of the following are true:

- partnership exists
- `goal_partnerships.status === 'active'`
- `goal_partnerships.notify_on_alerts === true`
- the goal still exists
- the goal is not completed
- the goal has at least one event
- the authenticated recipient would be the partner user

Any failure here should suppress alert creation cleanly.

## Suppression Rules

Alert generation must pass through these suppression layers in order:

1. `suppressed_no_partnership`
2. `suppressed_goal_completed`
3. `suppressed_paused`
4. `suppressed_notify_disabled`
5. `suppressed_no_signal`
6. `suppressed_grace`
7. `suppressed_duplicate`
8. `suppressed_rate_limited`

### `suppressed_no_signal`

No alert condition is currently true.

### `suppressed_grace`

A signal exists but the latest missed occurrence or inactivity condition is still inside the grace window.

### `suppressed_duplicate`

The same underlying alert state has already produced an alert and that state has not materially changed.

### `suppressed_rate_limited`

An alert was already delivered for the same partnership and goal within the configured cooldown.

Default v1 cooldown:

- 24 hours per partnership per goal

Recommended config key:

- `PARTNER_ALERT_RATE_LIMIT_HOURS=24`

## Candidate Alert Priority

When multiple alert types are true during the same evaluation, generate at most one partner-facing notification.

Priority order:

1. `consecutive_misses`
2. `streak_broken`
3. `inactivity`
4. `behind_pace`

Why:

- consecutive misses is the more extensible miss signal because it carries severity, not just yes/no
- streak break remains analytically important, but when both are true the miss count is the richer user-facing summary
- inactivity is more actionable than a purely numeric pace issue

All candidate reasons should still be preserved in observability metadata even if only one user-facing alert is created.

## Dedupe Model

Every candidate alert should produce a stable `dedupe_key`.

The exact format is implementation-specific, but it must include enough identity to distinguish a new problem from the same continuing problem.

Recommended components:

- `partnership_id`
- `goal_id`
- `alert_type`
- a signal fingerprint

Signal fingerprint examples:

- `streak_broken`: the first missed scheduled occurrence date that broke the streak
- `consecutive_misses`: the latest missed occurrence date plus current consecutive miss count
- `behind_pace`: the first threshold crossing into behind-pace territory, then only a new fingerprint if the gap worsens materially
- `inactivity`: the owner's `last_log_at` date or the inactivity threshold boundary date

If the same `dedupe_key` has already produced a notification, the evaluator should suppress a duplicate unless the state has materially advanced.

## Notification Content Rules

All notification copy must be:

- neutral
- brief
- non-shaming
- free of private text

### Allowed content

- goal title
- general alert reason
- safe snapshot-derived labels
- deep link target

### Forbidden content

- raw log notes
- moods
- feelings
- journal text
- excuses or reasons
- AI plan text
- full feedback history

### Example titles

- `streak_broken`: "They may have missed a scheduled check-in"
- `consecutive_misses`: "They may need help getting back on track"
- `behind_pace`: "They may be falling behind pace"
- `inactivity`: "They have not checked in for a few days"

### Tone by partnership role

Role affects wording only, never permissions or thresholds.

- `cheerleader`: softer encouragement-first language
- `drill_sergeant`: firmer, direct language without shame
- `silent`: minimal factual wording

## Deep Link Targets

Every partner-facing alert should deep link to the partnered goal snapshot view, not the owner's raw goal detail screens.

Required deep link data:

- `partnership_id`
- `goal_id`
- `notification_id`

Recommended frontend route target:

- partnership detail view for that goal

## Encouragement Flow

Each partner-facing alert can present one-tap encouragement presets.

### Rules

- presets only
- no free text
- encouragement is optional
- one encouragement per alert notification
- encouragement should not reopen or re-alert the partner

### Suggested preset set

- `youve_got_this`
- `small_steps_count`
- `reset_and_continue`
- `one_check_in_today`

Preset copy can vary by role tone, but the keys should stay stable for analytics and backend validation.

### Encouragement recipient behavior

When the partner sends an encouragement:

- create a `goal_partnership_encouragements` row
- optionally create an `encouragement_received` in-app notification for the goal owner

This owner-facing notification must also stay within the same privacy model:

- no partner free text
- no expanded raw feedback access

## Evaluation Flow

The evaluator should follow this sequence:

1. Load partnership, goal, owner, partner, and events.
2. Exit early if partnership is ineligible.
3. Generate scheduled occurrences using the shared occurrence service.
4. Build feedback lookups using actual persisted owner logs.
5. Determine:
    - missed eligible occurrences
    - consecutive miss count
    - current streak
    - last log date
    - inactivity days
    - points earned
    - points expected by today
    - pace status and pace delta
6. Derive all candidate alert types.
7. Apply grace suppression.
8. Choose the highest-priority candidate.
9. Build `dedupe_key`.
10. Apply duplicate suppression.
11. Apply 24h rate limiting.
12. Persist an alert event row with full outcome metadata.
13. If generated, create the recipient notification row.

## Scheduled Evaluator

The periodic evaluator exists to catch users who stop opening the app.

### Command behavior

- scan eligible active partnerships in chunks
- skip partnerships already evaluated recently if no relevant state changed
- run the same evaluator used by live triggers

### Scheduling

Recommended cadence:

- every day

Why daily:

- enough to catch dormant users without creating excessive background load
- aligned with a lower-noise v1 model and the lack of push delivery

### Candidate narrowing

The scheduled command should not blindly evaluate every partnership forever.
It should prioritize partnerships where:

- the owner has not logged recently
- the goal still has active schedule windows
- the partnership is active and alerts are enabled

## Frontend Scope For Phase 3

Phase 3 frontend work should include:

- notifications inbox screen
- unread badge or inbox indicator
- alert card UI
- deep link handling into partnership detail
- one-tap encouragement controls
- read / read-all behavior
- graceful invalid-partnership fallback when a deep link or cached detail screen points to a removed partnership

### Notifications inbox UI

Each item should show:

- title
- relative time
- goal title
- unread state
- tap target into partnership snapshot

The unread badge must be obvious because v1 has no push delivery.

It must not show:

- raw logs
- note excerpts
- mood history

### Partnership detail interplay

Alerts should always deep link to the existing Phase 2 partnership snapshot screen.
The snapshot remains the place where the partner sees:

- streak
- pace
- inactivity
- next scheduled event

The notification is only the entry point, not the full detail surface.

If the partnership has been removed, the frontend should route back to the partnerships list and show a friendly notice rather than leaving the user on a broken screen.

## Settings Behavior

Phase 3 must respect the existing settings exactly:

### `status = paused`

- no new alerts
- no encouragement prompts from new alerts
- snapshot remains readable

### `notify_on_alerts = false`

- no new alerts
- snapshot remains readable
- this is not the same as `paused`

### unlinked / deleted partnership

- no new alerts
- no new encouragements
- linked notifications should no longer deep link into protected data
- cascade behavior may remove orphaned records or allow only safe historical rows, but the user must not regain access to removed partnership data

## Observability Requirements

Phase 3 must leave a debuggable trail.

For each evaluation, the system should be able to answer:

- what triggered the evaluation
- what candidate alert types were true
- why an alert was or was not created
- what dedupe key was used
- whether cooldown suppression happened
- what safe metrics were visible at evaluation time

This is necessary for:

- debugging false positives
- tuning thresholds
- confirming pause and mute behavior
- understanding why a user did or did not get an alert

Generated alerts should be retained longer than suppressed outcomes.
Suppressed observability should be compacted, sampled, or pruned on a short retention window rather than stored forever.

## Security And Privacy Requirements

- Notification payloads must be derived from safe signals only.
- Partner notifications must never leak owner-only raw data.
- Recipient authorization must be enforced on every notification read and encouragement action.
- Partner notifications must not grant any route to owner-only endpoints.
- Alerts must never be generated from unsynced client assumptions.

- `PARTNER_ALERT_RATE_LIMIT_HOURS=24`

- `PARTNER_ALERT_INACTIVITY_DAYS=3`

These should be configurable, not hard-coded.

## Acceptance Criteria

Phase 3 is complete when all of the following are true:

- a successful log submission can trigger evaluation without leaking raw data
- no routine high-churn read endpoint is used as the primary evaluator trigger
- scheduled daily scans catch dormant users
- due-today unlogged events do not alert prematurely
- identical alert state does not spam repeated notifications
- no partnership receives more than one alert per goal per 24 hours
- paused partnerships do not create alerts
- partnerships with `notify_on_alerts = false` do not create alerts
- the partner can read notifications and mark them read
- the partner can deep link into the safe partnership snapshot
- encouragements use preset-only controls
- no free-text communication is introduced
- alert creation and suppression are observable in stored evaluator records

## Rollout Recommendation

Implement Phase 3 in this order:

1. Extract shared occurrence generation from the snapshot service.
2. Build evaluator + alert event persistence.
3. Build notification persistence + read APIs.
4. Add encouragement flow.
5. Add scheduled command and scheduler registration.
6. Integrate frontend inbox and deep links.

This keeps the alert engine grounded in the same scheduling logic already validated during Phase 2.
